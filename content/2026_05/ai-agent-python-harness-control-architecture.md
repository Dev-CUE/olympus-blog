## 1. 자율형 에이전트를 꿈꾸다 마주한 현타

멀티 에이전트 구조를 설계하다 보면 한 번쯤 같은 결론에 도달한다.

처음에는 그럴듯하다.

- Zeus는 인프라와 보안을 담당한다.
- Hera는 법무, 회계, 일정, 문서 정리를 담당한다.
- Athena는 개발, 테스트, 배포를 담당한다.
- Router는 요청을 분류하고 적절한 에이전트에게 넘긴다.
- 에이전트끼리는 서로 검토하고, 보완하고, 승인한다.

겉으로 보면 자율형 조직처럼 보인다.  
하지만 실제로 구현 단계에 들어가면 구조는 빠르게 복잡해진다.

에이전트가 에이전트를 감시한다.  
감시한 결과를 다시 다른 에이전트가 검토한다.  
Router는 누구에게 보낼지 판단한다.  
그 판단의 근거를 또 기록해야 한다.  
실패하면 재시도해야 하고, 재시도 실패 시 fallback을 붙여야 한다.  
중간 상태를 저장하지 않으면 장기 작업은 끊긴다.  
저장하면 이번에는 잘못된 기억이 다음 판단에 섞인다.

여기서 첫 번째 현타가 온다.

문제는 “에이전트를 몇 개로 나눌 것인가”가 아니다.  
문제는 “누가 프로세스를 결정론적으로 통제할 것인가”다.

자율형 에이전트라는 말은 매력적이다.  
그러나 엔터프라이즈 시스템에서 필요한 것은 매력적인 개념이 아니라 재현 가능한 실행이다.

결국 멀티 에이전트 상호 감시 구조는 닭과 달걀의 문제에 부딪힌다.

- 에이전트가 똑똑해야 통제를 맡길 수 있다.
- 그러나 통제를 맡기려면 먼저 에이전트가 신뢰 가능해야 한다.
- 신뢰 가능성을 검증하려면 외부 통제 구조가 필요하다.
- 외부 통제 구조가 필요하다면, 자율성이 핵심이 아니다.

이 지점에서 “AI 에이전트에게 자율성을 주면 알아서 일할 것”이라는 가정은 깨진다.

자율성은 출발점이 아니다.  
자율성은 통제 구조 위에서 제한적으로 허용되는 결과물이다.

## 2. LLM의 민낯: 박사급 지식과 주니어급 일머리

LLM의 성능을 낮게 평가할 필요는 없다.  
지식의 폭만 보면 이미 상당수 업무 영역에서 인간 전문가 수준의 답변을 생성한다.

문제는 지식이 아니다.  
문제는 프로세스다.

LLM은 개념을 설명할 수 있다.  
아키텍처를 제안할 수 있다.  
코드를 작성할 수 있다.  
문서를 요약할 수 있다.  
회의록도 만들 수 있다.

하지만 이것이 곧 일을 끝낼 수 있다는 뜻은 아니다.

LLM에는 인간이 당연하게 갖고 있는 시간 감각이 없다.  
여기서 말하는 시간 감각은 “현재 시각을 안다”는 의미가 아니다.  
작업의 전후관계, 대기, 재시도, 완료 조건, 실패 조건, 상태 전이를 스스로 안정적으로 유지하는 능력이다.

시스템 관점에서 보면 LLM은 Clock Cycle이 없다.

즉, 다음과 같은 실행 감각이 약하다.

- 지금 이 작업이 몇 번째 단계인지
- 이전 단계가 실제로 완료되었는지
- 실패했는지, 지연 중인지, 대기 중인지
- 재시도해야 하는지, 중단해야 하는지
- 동일한 지시를 반복하고 있는지
- 오래된 맥락이 현재 판단에 섞였는지

LLM은 한 번의 호출 안에서는 매우 유능하다.  
하지만 여러 단계에 걸친 업무에서는 쉽게 흐트러진다.

그래서 LLM은 “기억 상실증에 걸린 주니어”에 가깝다.

스펙은 이상하다.

- 지식: 박사급
- 문장력: 상급
- 코드 생성력: 실무 투입 가능
- 업무 지속성: 낮음
- 상태 관리: 낮음
- 책임 경계 인식: 낮음
- 완료 조건 검증: 외부 장치 필요
- 실수 반복 방지: 외부 기록 필요

이 모순을 이해해야 한다.

LLM이 똑똑하다는 사실은 맞다.  
하지만 똑똑하다는 것이 곧 일을 맡길 수 있다는 뜻은 아니다.

엔터프라이즈 프로젝트에서 중요한 것은 단발성 답변의 품질이 아니다.  
중요한 것은 다음이다.

- 누가 작업을 시작했는가
- 어떤 입력으로 실행했는가
- 어떤 상태를 거쳤는가
- 어떤 검증을 통과했는가
- 실패 시 어디서 멈췄는가
- 다시 실행해도 같은 결과가 나오는가

이것이 프로세스다.  
LLM은 프로세스를 설명할 수는 있지만, 프로세스 그 자체가 되지는 못한다.

## 3. 해결책은 파이썬 하네스다

해결책은 에이전트에게 더 많은 자유를 주는 것이 아니다.  
해결책은 에이전트를 더 단단한 하네스 안에 넣는 것이다.

여기서 하네스는 단순한 실행 스크립트가 아니다.  
AI가 생성한 출력을 결정론적 코드가 검증하고, 반복하고, 중단하고, 기록하는 오케스트레이션 구조다.

핵심은 명확하다.

LLM이 통제하는 것이 아니다.  
파이썬 코드가 통제한다.

LLM은 판단 후보를 생성한다.  
파이썬 하네스는 그 후보가 실행 가능한지 검증한다.  
검증에 실패하면 다시 요청한다.  
반복 횟수를 초과하면 중단한다.  
성공하면 다음 단계로 넘긴다.  
모든 단계는 로그와 상태로 남긴다.

가장 단순한 형태는 다음과 같다.

```python
while attempt < max_attempts:
    response = call_llm(task_packet)

    parsed = validate_with_pydantic(response)

    if parsed.ok:
        result = execute_next_step(parsed)
        save_state(result)
        break

    attempt += 1

if attempt >= max_attempts:
    raise WorkflowFailed("LLM output failed validation")
```

이 구조에서 중요한 것은 `while`이다.

많은 사람이 AI 자동화를 말할 때 모델 성능부터 본다.  
하지만 실제 자동화에서 먼저 필요한 것은 반복 제어다.

- 몇 번 시도할 것인가
- 어떤 조건에서 실패로 볼 것인가
- 어떤 조건에서 다음 단계로 넘어갈 것인가
- 어떤 출력을 폐기할 것인가
- 어디까지 자동화하고 어디서 인간 승인을 받을 것인가

이것은 LLM의 역할이 아니다.  
이것은 하네스의 역할이다.

### Pydantic 검증의 의미

Pydantic 검증은 단순히 JSON 모양을 맞추는 도구가 아니다.  
LLM의 자유 출력을 업무 시스템이 소비 가능한 계약으로 바꾸는 경계선이다.

예를 들어 Router가 다음 작업자를 결정해야 한다면 자유문을 받아서는 안 된다.

나쁜 출력은 이런 형태다.

```text
이 요청은 개발과 관련이 있으므로 Athena에게 보내는 것이 좋겠습니다.
다만 보안 요소도 있으니 Zeus가 확인하면 좋겠습니다.
```

사람이 읽기에는 괜찮다.  
시스템이 처리하기에는 부적합하다.

좋은 출력은 이런 형태다.

```json
{
  "route": "athena",
  "cc": ["zeus"],
  "task_type": "code_change",
  "sensitivity": "medium",
  "needs_approval": true,
  "reason_code": "CODE_WITH_INFRA_IMPACT"
}
```

그리고 이 출력은 Pydantic으로 검증되어야 한다.

```python
from pydantic import BaseModel
from typing import Literal

class RouteDecision(BaseModel):
    route: Literal["zeus", "hera", "athena"]
    cc: list[Literal["zeus", "hera", "athena"]]
    task_type: Literal["code_change", "legal", "infra", "accounting", "research"]
    sensitivity: Literal["low", "medium", "high"]
    needs_approval: bool
    reason_code: str
```

이 구조가 있어야 LLM 출력은 시스템 입력이 된다.  
그 전까지 LLM 출력은 문장일 뿐이다.

### WBS 자동화의 핵심은 생성이 아니라 통제다

WBS 자동화도 마찬가지다.

LLM에게 “작업을 나눠줘”라고 말하면 그럴듯한 목록은 나온다.  
하지만 실무에서 필요한 WBS는 목록이 아니다.

필요한 것은 실행 가능한 작업 분할 구조도다.

각 작업은 다음 정보를 가져야 한다.

- 작업 ID
- 선행 작업
- 담당 역할
- 입력 산출물
- 출력 산출물
- 완료 조건
- 검증 방법
- 실패 시 처리 방식
- 승인 필요 여부

즉, WBS 자동화의 본질은 작업 생성이 아니다.  
작업을 검증 가능한 단위로 강제 분해하는 것이다.

LLM은 WBS 초안을 만들 수 있다.  
하지만 WBS의 일관성은 하네스가 검증해야 한다.

예를 들어 다음 조건은 코드가 검사해야 한다.

- 모든 작업 ID가 유일한가
- 선행 작업이 존재하는가
- 순환 의존성이 없는가
- 완료 조건이 비어 있지 않은가
- 검증 방법이 명시되어 있는가
- 승인 필요 작업이 별도 게이트를 갖는가

이것이 결정론적 통제다.

LLM에게 “잘해줘”라고 말하는 것은 통제가 아니다.  
스키마, 루프, 상태 저장, 실패 조건, 승인 게이트로 묶는 것이 통제다.

## 4. 인간 PM 가치의 재발견

AI 에이전트가 발전할수록 인간 PM의 가치가 낮아질 것이라는 주장은 절반만 맞다.

단순 일정 관리, 회의록 작성, 초안 생성, 상태 요약의 가치는 낮아진다.  
그 영역은 자동화된다.

하지만 엔터프라이즈 프로젝트에서 PM의 핵심 가치는 원래 거기에 있지 않았다.

진짜 가치는 다음에 있다.

- 업무의 인과관계를 이해하는 능력
- 도메인 제약을 구조화하는 능력
- 이해관계자의 암묵지를 실행 규칙으로 바꾸는 능력
- 완료 조건과 검증 조건을 정의하는 능력
- 책임 경계와 승인 흐름을 설계하는 능력
- 실패 시 중단 지점을 판단하는 능력

이 영역은 쉽게 자동화되지 않는다.  
오히려 AI가 도입될수록 더 중요해진다.

AI는 더 많은 초안을 만든다.  
더 많은 선택지를 만든다.  
더 많은 코드를 만든다.  
더 많은 문서를 만든다.

따라서 인간 설계자는 더 엄격한 통제 구조를 가져야 한다.

여기서 바퀴를 다시 발명해야 하는 이유가 생긴다.

기성 에이전트 프레임워크는 유용하다.  
하지만 특정 기업의 업무 인과관계, 승인 구조, 보안 경계, 도메인 데이터, 실패 허용 범위까지 자동으로 이해하지는 못한다.

특히 B2B 시스템, 제조 IT, SI 프로젝트에서는 더 그렇다.

제조 현장의 프로세스는 단순한 CRUD가 아니다.  
ERP, MES, POP, SCM, 회계, 구매, 생산, 품질, 출하가 연결된다.  
하나의 판단 오류가 업무 흐름 전체를 흔든다.

이 영역에서 필요한 것은 범용 자율 에이전트가 아니다.  
도메인 지식과 비즈니스 인과관계를 반영한 통제 아키텍처다.

RAG도 같은 맥락이다.

RAG는 문서를 검색해주는 장치가 아니다.  
업무 판단에 필요한 근거를 제한된 범위에서 공급하는 장치다.

잘못 설계된 RAG는 오래된 문서와 임시 요약을 사실처럼 주입한다.  
잘 설계된 RAG는 검증된 사실, 결정 사항, 원문 근거, 현재 작업 상태를 분리해서 제공한다.

결국 핵심은 같다.

AI에게 모든 것을 맡기지 않는다.  
AI가 잘하는 영역만 맡긴다.  
나머지는 결정론적 코드와 인간 설계자가 통제한다.

자율형 에이전트의 환상은 여기서 끝난다.

실무에서 필요한 것은 완전 자율이 아니다.  
통제된 반자율이다.

LLM은 엔진이다.  
하네스는 변속기와 브레이크다.  
PM은 도로와 목적지를 아는 사람이다.

엔진만으로는 시스템이 되지 않는다.
